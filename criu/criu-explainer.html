Checkpoint / Restore In Userspace

把正在跑的 process
凍結成檔案，再叫回來

CRIU 把一整棵 Linux process tree 的狀態（記憶體、暫存器、開著的檔案、socket、PID）寫成一組 image 檔。之後從這些檔案重建，程式從被凍結的那一條指令繼續跑，完全不知道自己停過。

只支援 Linux 需要 CAP_SYS_ADMIN criu 4.3 GPU：cuda-checkpoint

一個 process 由什麼組成

怎麼做到的

Dump 拆開 process，restore 再一片一片組回去

CRIU 全部在 user space 完成，只用 kernel 已有的介面，不需要特製 kernel。最巧妙的兩步是 dump 時的「parasite」與 restore 時的「restorer」。

Dump criu dump -t PID

  1. 凍結整棵 tree用 PTRACE_SEIZE + PTRACE_INTERRUPT 停住每個 thread，或用 freezer cgroup。從這裡開始計算「frozen time」。
  2. 從外面收集讀 /proc/PID/ 底下的 maps、fd、fdinfo、status、ns；用 netlink sock_diag 查 socket。
  3. 注入 parasite把一小段程式碼塞進目標 process 的位址空間並執行，從「裡面」讀外面讀不到的東西，並把記憶體 page 用 vmsplice 送出來。
  4. 寫出 images所有狀態寫成 *.img（protobuf），記憶體寫成 pages-*.img。
  5. 移除 parasite把 process 還原成注入前的樣子。
  6. 殺掉或放行預設 kill 整棵 tree；加 --leave-running 就讓它繼續跑，等於拍了一張 snapshot。

Restore criu restore -D img

  1. 用同樣的 PID 重建 tree照 pstree.img 用 clone3(set_tid) fork 出每個 process，所以原本的 PID 必須是空的。
  2. 重建共享資源namespaces、檔案（重新 open 並 seek 回 offset，檔案大小必須一致）、pipe、socket（TCP_REPAIR 把序號塞回去）。
  3. 準備記憶體按 mm-*.img 建好位址對映，把 pages-*.img 讀進來。
  4. 切換到 restorerCRIU 自己的程式碼此時還占著這個 process 的位址空間；跳到一小段獨立的 restorer blob，把 CRIU 自己 unmap 掉，換上最終的記憶體布局。
  5. 回到凍結的那一條指令恢復 timer、credentials、thread，最後用 rt_sigreturn 載入當初存下的暫存器，process 從原處繼續執行。
縮短凍結時間 · live migration 的原理

先邊跑邊複製，最後只凍結一下下

一般 dump 必須在 process 停住時寫出全部記憶體，記憶體越大停越久。criu pre-dump --track-mem 只短暫停住收集 page 清單，然後讓 process 繼續跑、同時複製記憶體，並開啟 kernel 的 soft-dirty 追蹤。下一輪只寫上次之後被改過的 page。

範例 06 的實測：一個持續改寫 4 MiB 的 1 GiB process。停機時間從 400 ms 降到 137 ms，最後一次只需要寫 40 MiB。三次的 images 串成一條鏈（final → pre2 → pre1），restore 時沿著鏈把記憶體拼回來。

記憶體改得比複製還快時，pre-dump 永遠收斂不了，這也是 live migration 的極限。

GPU process

先讓 GPU process 變回「普通 process」，CRIU 才接得手

CRIU 不懂 GPU，GPU 記憶體和 driver 狀態都不在它讀得到的地方。NVIDIA 的 cuda-checkpoint（driver ≥ 550）負責把 GPU 狀態搬回 host memory 並釋放 GPU；之後對 CRIU 來說，這就是一個純 CPU process。

running lock locked checkpoint checkpointed criu dump → 檔案 → restore restore locked unlock running

lock：等正在跑的 CUDA work 結束，擋住新的 CUDA API call。checkpoint：把 device memory 複製到 host，釋放 GPU（nvidia-smi 上看不到它了）。restore：放回 GPU，可以用 --device-map 換卡。unlock：讓 CUDA 繼續。--toggle 一次做完前兩步或後兩步。

# 08_cuda.sh：counter 存在 GPU 記憶體裡，checkpoint 後換到另一張 A100
gpu counter=2  (running on PCI 0000:0F:00.0)
$ cuda-checkpoint --action lock --pid 5304         → locked
$ cuda-checkpoint --action checkpoint --pid 5304   → checkpointed
$ criu dump -t 5304 -D img                         451M img
$ criu restore -D img -d                           → 仍是 checkpointed
$ cuda-checkpoint --action restore --pid 5304 --device-map '<GPU0>=<GPU1>,<GPU1>=<GPU0>,…'
$ cuda-checkpoint --action unlock --pid 5304       → running
gpu counter=3  (running on PCI 0000:0F:00.0)   ← 從 GPU 記憶體接著數
$ nvidia-smi --query-compute-apps=pid,gpu_bus_id
5304, 00000000:15:00.0                          ← 實際上已經在另一張卡

換卡對 process 是透明的：它還以為自己在 device 0，連印出的 PCI bus id 都是舊的。--device-map 必須涵蓋 process 看得到的所有 GPU，沒換的就對映到自己。Image 大小約等於 GPU 記憶體用量（418 MiB → 451 MB），大模型動輒數十 GB，I/O 會是主要成本。

存與不存

CRIU 存的是 process，不是它周圍的世界

會存

  • 所有記憶體 page
  • CPU 暫存器、signal、credentials、timer
  • fd 的路徑、flags、offset
  • Pipe、unix socket；TCP 需加 --tcp-established
  • Process tree、PID、namespaces

不會存

  • 檔案內容：restore 時檔案必須存在且大小一致
  • 連線的另一端：server 要自己還活著
  • GPU 狀態：要先用 cuda-checkpoint
  • 一般硬體裝置的狀態
  • Tree 外面的 process
Images 等於 process 的完整記憶體。範例 07 直接用 grep 就在 pages-*.img 裡找到程式記憶體中的字串。Token、密碼、資料都在裡面，要當機密保管。
踩過的坑

這些錯誤都是寫範例時真的遇到的

檔案在 snapshot 之後變了

Error (criu/files-reg.c:2175): File .../out.log has bad size 72 (expect 32)

process 拍照後 out.log 又被寫入。CRIU 只記得 offset，發現檔案大小對不上就拒絕 restore。

解法：把檔案和 process 一起 snapshot。容器的 checkpoint 會把 rootfs 的變更一起打包，也是為了這個。

PID 被 zombie 佔住

Error (criu/cr-restore.c:1245): Can't fork for 4448: File exists

Pod 的 PID 1 是 sleep infinity，不會回收 zombie。被交給 PID 1 的 orphan 結束後一直佔著 PID，CRIU 就無法用原本的 PID restore。

解法：容器 PID 1 用會回收 zombie 的 init（tini、dumb-init），或用 PR_SET_CHILD_SUBREAPER 自己當 subreaper（範例的 reaper.py）。Restore 到新的 Pod 就有全新的 PID namespace，不會撞到。

有已建立的 TCP 連線

Error (criu/sk-inet.c:201): inet: Connected TCP socket, consider using --tcp-established option.

預設不 dump 已建立的 TCP 連線。加上 --tcp-established 後，CRIU 用 TCP_REPAIR 存下序號與佇列。凍結期間要用 --network-lock（iptables 或 nftables）擋住封包，否則對方會收到 RST。

跨機器搬移：IP 也要跟著搬，否則 TCP 的 4-tuple 對不上。

權限不夠

CRIU 需要 CAP_SYS_ADMIN（或 CAP_CHECKPOINT_RESTORE 加上其他權限），在容器裡通常要 privileged 並關掉 seccomp。這也是只在專用的實驗 Pod 裡測、不在共用環境裡開的原因。

用在哪裡

從 live migration 到秒級啟動推論服務

Live migration

pre-dump 多輪後只停機一下，把 process 搬到另一台機器。

快速啟動

把載入完模型、暖機完的推論 process 存成 image，之後直接 restore，跳過載入權重與 CUDA graph capture。

容錯與搶佔

長時間的 job 定期 checkpoint，節點被收回或維修時從最近的 checkpoint 接著跑。

保存問題現場

把出問題的 process 凍結起來，之後再拿出來分析。

Kubernetes 與容器

kubelet 的 checkpoint API（ContainerCheckpoint）透過 CRI-O 呼叫 CRIU；Podman 有 container checkpoint / restore。

ModelExpress

pause_serving / resume_serving 讓推論 worker 安全地經歷 cuda-checkpoint + CRIU：先停止 P2P 分享、釋放 NIXL 鎖住的記憶體，restore 後再重新註冊。
